# MASTER IMPLEMENTATION PROMPT — PLUTUS Server-Side Hardening

## المهمة

أنت مهندس Full-Stack وأمن تطبيقات تعمل على مستودع PLUTUS المتصل مباشرة. نفّذ تحسينات الأمان ومحرك المخاطر على الخادم وقاعدة البيانات **فقط**، بالتسلسل الوارد أدناه. لا تتجاوز مرحلة أو تبدأ ميزات إضافية قبل اجتياز اختبارات المرحلة الحالية.

## قيد غير قابل للتفاوض: لا تغيّر واجهة التطبيق بصرياً

> **ممنوع منعاً باتاً تغيير تصميم واجهة التداول أو شكل التطبيق.**
>
> لا تغيّر بصرياً `public/plotos/index.html`، ولا الألوان أو الخطوط أو الأزرار أو ترتيب النوافذ أو الرسوم البيانية أو responsive design أو واجهة الهاتف. لا تحوّل شاشة التداول إلى React ولا تعِد بناء الواجهة. يجب أن تبقى مطابقة تقريباً للحالة الحالية.
>
> اجعل التغييرات في Backend/Database/Trading Engine/API فقط. يُسمح بتعديل Frontend برمجياً فقط عند الضرورة لربط الواجهة الحالية بحالة الخادم، بأقل diff ممكن ومن دون تغيير DOM المرئي أو CSS أو النصوص أو الترتيب. قبل أي تعديل frontend، اشرح ضرورته وأثبت عدم وجود بديل خادمي.

## قواعد المشروع والأمان

1. أنشئ فرع عمل جديداً من `main`، ولا تعدّل تاريخ Git المنشور ولا تستخدم force-push. لا تدمج أو تنشر إلى `main` تلقائياً؛ اعرض diff والاختبارات للمراجعة.
2. ابدأ بمراجعة `AGENTS.md` و`SECURITY_AND_DATABASE.md` وجميع ملفات backend وmigrations الحالية. لا تفترض أن الملفات المحلية تطابق قاعدة Supabase الحية.
3. **لا تطبق أي DDL أو migration على Supabase** ولا تنشئ فروع/موارد مدفوعة. أضف SQL إلى المستودع فقط. اعرض الأثر وخطة rollback واطلب موافقة صريحة قبل أي تغيير خارجي.
4. لا تنشئ مستخدمين أو حسابات ممولة وهمية، ولا تستخدم بيانات أشخاص حقيقيين أو بيانات اعتماد إنتاجية. لا تنفذ دفعاً أو أوامر وسيط حقيقية؛ التداول محاكاة فقط.
5. لا تضع أسراراً في Frontend أو Git أو السجلات. لا تسجل Authorization headers أو كلمات المرور أو محتوى الطلبات الحساس. أدوار المستخدمين تؤخذ من Supabase `app_metadata` الموثوق فقط؛ قيم العميل ليست صلاحيات.
6. حافظ على NOWPayments: لا تحذف ولا تعِد توجيه مسارات invoice/webhook، ولا تمنح تمويلاً أو entitlement تلقائياً بسبب webhook. حافظ على spread logic والسلوك الحاليين ما لم يثبت اختبار محدد وجود خلل.
7. لا تستخدم `pf_users_data.blob` كمصدر حقيقة للأرصدة أو الصفقات. لا تمنح العميل صلاحية كتابة الحسابات أو الأرصدة أو قواعد المخاطر أو سجل التدقيق. لا تدّع أن الحماية أصبحت نافذة قبل نشر migration والتحقق من RLS فعلياً.
8. حزمة `backend/src/security.ts` و`backend/src/risk.ts` وملف migration المرفق **نقطة بدء ومادة للمراجعة وليست كوداً معتمداً للنسخ الأعمى**. طابق كل نوع واسم جدول وRPC مع المستودع، واكتب اختبارات تغطيه.

## بنية المشروع الحالية التي يجب الحفاظ عليها

- واجهة التداول: `public/plotos/index.html`؛ لا إعادة تصميم.
- API: `backend/src/api.ts` (Fastify 5، Zod، Supabase service client).
- منطق المجال: `backend/src/domain.ts`؛ أسعار Biquote وفحص freshness.
- عامل الأسعار: `backend/src/worker.ts`؛ لا يقبل أسعار تنفيذ من العميل.
- مدخل العملية الموحدة: `backend/src/start.ts`.
- مخطط المحرك الحالي: `supabase/migrations/20261016090000_server_side_paper_engine.sql`.
- سجل `pf_security_audit` موجود للمراجعات والطلبات، وله قيد `CHECK` محدود؛ لا تكسره ولا تعِد استخدامه لأحداث المحرك دون مراجعة أثر ذلك. يوجد أيضاً سجل تداول `pf_engine_trades_history`.
- `pf_engine_accounts` يحتوي الرصيد والرافعة وحد الهامش، و`pf_engine_quotes` يخزن `quote_at` و`received_at`؛ الأدوات تحمل `tick_size` و`tick_value` و`contract_size`.
- تكامل NOWPayments قائم في `src/routes/api/public/payments/`، وبيانات الدفع ليست صلاحية لمنح حساب.

## التنفيذ — بوابات قبول متسلسلة

### المرحلة 0 — خط أساس وقيود التغيير

- سجل commit الأساس، نفّذ الاختبارات الحالية، ودوّن حالة الملفات قبل التعديل.
- أثبت أن واجهة التداول لم تتغير بصرياً: لا تغييرات CSS/markup/الأصول أو النصوص. إذا اضطررت إلى تعديل ربط API فقط، اجعل التغيير معزولاً واختبر diff بصرياً على مقاسات الهاتف والويب.
- لا تبدأ المرحلة التالية حتى يصبح خط الأساس واضحاً وتُحصر المخاطر الحالية.

### المرحلة 1 — حدود الثقة وأمن API

- أزل اعتماد العميل/`localStorage` كمصدر حقيقة للأرصدة والطلبات والصفقات؛ اجعل الخادم هو المصدر، مع الحفاظ على عرض الواجهة كما هو.
- تحقق من Supabase bearer token خادمياً لكل عملية، واربط كل مورد بـ`user.id`؛ تحقق من ADMIN/FINANCE عبر metadata موثوقة في الخادم/RPC فقط.
- أدمج `security.ts` بعد مراجعة حدوده: rate limiting، security headers، request IDs، CORS مضبوط. لا تثق بـ`X-Forwarded-For` إلا خلف proxy معروف ومحدد. حد المعدلات داخل الذاكرة لا يكفي لتعدد النسخ؛ وثّق backend موزعاً مثل Redis/Key Value قبل الإنتاج.
- أضف سجلاً خادمياً للعمليات الأمنية/الإدارية. لا تسمح بكتابة العميل. افصل أحداث محرك التداول عن `pf_security_audit` إن كان تعديل constraint أو معنى السجل يسبب تعارضاً.
- اختبر عزل مستخدمين، رفض role injection، الطلبات غير الموثقة، CORS، 429، request IDs، وعدم تسريب الأسرار.
- **بوابة:** لا تبدأ Risk Engine قبل نجاح اختبارات هذه المرحلة وtypecheck.

### المرحلة 2 — Risk Engine وProp-firm rules

- اجعل الحسابات والمقاييس Server-side: equity، floating P&L، used/free margin، margin level، peak equity، daily/total drawdown.
- عرّف بوضوح اليوم/المنطقة الزمنية وقاعدة إعادة تعيين daily drawdown. اختبر حدوداً عند 0% و100%، نهاية اليوم، والساعة الصيفية إن كانت المنطقة غير UTC.
- نفّذ static initial-balance وtrailing peak drawdown حسب profile صريح. أضف profit target وminimum trading days وconsistency rule.
- احسب أهلية payout كمحاكاة/قرار داخلي فقط: لا اتصال دفع ولا إنشاء transaction مالي ولا اعتماد تلقائي. أبقِ الموافقة الإدارية منفصلة.
- احسب realized P&L وأيام التداول والاتساق من مجاميع كاملة موثوقة في قاعدة البيانات، لا من آخر N صفقة أو بيانات العميل. لا تستخدم تقدير payout المرفق كأساس لدفعة؛ يجب طرح الطلبات/السحوبات المقبولة سابقاً بقيد ذري قبل اعتماد أي أهلية أو مبلغ.
- Economic-news protection **معطل افتراضياً** حتى يوجد مزود موثوق ومصرّح. لا تختلق أحداثاً ولا تعتمد على بيانات غير موثقة. عند تفعيل الحماية، لا تسمح للأحداث غير المتحقق منها بتجاوز قواعد التداول؛ اختبر سلوك انقطاع المصدر.
- أساس الحسابات يفترض أن `tick_value` بعملة الحساب أو تم تحويله بشكل موثوق؛ وثّق ذلك ولا تخفِ غياب تحويل العملات.
- اختبر long/short، bid/ask، instrument metadata المفقودة، quote stale/غير مرتب، margin، peak/day reset، drawdown breach، target، consistency، payouts، وأحداث الأخبار الموثقة.
- **بوابة:** لا تبدأ سباقات التنفيذ قبل ثبات الحسابات واختبارات القواعد.

### المرحلة 3 — سلامة التنفيذ والتزامن

- اجعل كل order/close/partial close idempotent ومقيداً بمفتاح طلب مرتبط بالمستخدم والمورد، لا بمفتاح عالمي يمكن سرقته.
- ضع القيود/row locks الصحيحة في RPC، مع نفس transaction لتعديل position/account/ledger/history/metrics/audit. اختبر عمليتين متزامنتين على الصفقة نفسها وطلبات مكررة عبر اتصالات منفصلة.
- سجّل execution metadata ذات معنى: quote timestamp/source، engine version، price basis، idempotency key، reason؛ لا تسجل أسراراً أو PII غير ضرورية.
- ارفض quote stale أو غير مرتب عند فتح/تعديل/إغلاق العملية؛ لا تستعمل cache محلياً للتفويض أو التنفيذ.
- احمِ ledger والرصيد من التعديل المباشر؛ تحقق من invariants قبل وبعد الإغلاق الجزئي، margin، stop-out. لا تُحدث رصيداً خارج transaction ذرية.
- **بوابة:** لا تبدأ فحوص التسليم حتى تنجح اختبارات التزامن وRPC.

### المرحلة 4 — التحقق والتسليم

شغّل وسجّل النتائج الفعلية لهذه الأوامر من جذر المشروع، وبـ`backend/` عند الحاجة:

- `bun install --frozen-lockfile`
- `bun run test`
- `bun run lint`
- `bun run build`
- `cd backend && bun install --frozen-lockfile && bun run typecheck && bun run test`
- اختبارات تكامل/تزامن باستخدام قاعدة اختبار أو staging معزولة فقط؛ لا تستخدم الإنتاج.

أضف اختباراً يثبت عدم تغيّر الواجهة المرئية وعدم حذف NOWPayments أو spread logic. اذكر أي فشل أو تحذير كما هو؛ لا تتجاوزه ولا تزعم نجاح أمر لم يُشغّل. لا تضف ميزات أخرى قبل نجاح المراحل الأربع.

## تقرير النهاية المطلوب

اعرض commit/branch، الملفات المتغيرة، نتائج كل اختبار، أي تغييرات frontend (إن وجدت) وسببها، ما لم يُطبق على قاعدة البيانات، وحدود rate limiter/مزود الأخبار/تحويل عملة الحساب. قدم migration للمراجعة فقط، ولا تنشرها ولا تنشر backend دون إذن منفصل.
