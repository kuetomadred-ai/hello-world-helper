# خادم ومحرك التداول المحاكى

هذا مسار backend منفصل عن واجهة التداول القديمة. التنفيذ **محاكاة فقط**؛ لا توجد واجهة لإرسال أوامر إلى وسيط. قاعدة البيانات هي مصدر حقيقة الحساب والصفقات، وتأتي الأسعار من Biquote على الخادم. لا تضع `SUPABASE_SERVICE_ROLE_KEY` في تطبيق الهاتف أو الويب.

## المتطلبات

- Bun 1.4.3 (أو Node.js 22+ للتطوير)
- Supabase URL + anon key + service-role key (الخادمي فقط)
- السماح لشبكة/خادم التشغيل بالاتصال بـBiquote SignalR
- migration الخادم الأساسية وسجل الصفقات مطبّقان على قاعدة المشروع الحية: `20261021120244_server_side_paper_engine` و`20261021120308_paper_trade_history`.

## التشغيل المحلي

```sh
cd backend
bun install --frozen-lockfile
cp .env.example .env
bun run typecheck
bun test
bun run start
# أو للتشخيص، شغّل bun run api وbun run worker في عمليتين منفصلتين.
```

المتغيرات موجودة في `.env.example`. `CORS_ORIGINS` قائمة مضيفي الواجهة مفصولة بفواصل. `ENGINE_SYMBOLS` قائمة allowlist؛ يرفض العامل الأدوات التي لا يعيد مزود السعر لها tick size وtick value موجبَين.

## API الحالي

- `GET /health`
- `GET /v1/trading/state` و`GET /v1/accounts/:id/state` — يعيدان حالة حسابات المستخدم الموثق فقط.
- `GET /v1/admin/accounts` و`POST /v1/admin/accounts` — يتطلبان مستخدم ADMIN موثقاً؛ إنشاء الحساب يتم عبر RPC موثوق.
- `POST /v1/orders` — يتطلب `Authorization: Bearer <Supabase access token>` و`accountId, requestId, symbol, side, type, lots`؛ `requestId` مفتاح idempotency.
- `POST /v1/positions/:id/close` و`/close-partial` — الإغلاق بسعر Biquote الخادمي مع حد الاحتفاظ الأدنى.
- `POST /v1/positions/:id/protection` — تعديل SL/TP بعد تحقق الخادم من السعر.
- `POST /v1/orders/:id/modify` و`/cancel` — تعديل/إلغاء أوامر المستخدم المعلقة فقط.

الخادم يتحقق من الجلسة عبر Supabase Auth ثم ينفذ RPC بصلاحيات الخدمة. لا يقبل سعر تنفيذ من العميل. العامل الدائم يشترك في بث Biquote ويستدعي RPC ذرياً لمراقبة SL/TP وتشغيل LIMIT/STOP.

## ربط واجهة Plutus

قبل نشر العميل، اضبط `window.PLUTUS_ENGINE_API_URL` في `public/plotos/engine-config.js` إلى origin الخاص بالخادم، ثم أضف origin الواجهة إلى `CORS_ORIGINS`. لا تضع أي مفتاح خادمي في ملف الواجهة. يقرأ العميل الحسابات والصفقات من `/v1/trading/state` ويرسل أوامر التداول إلى API. لا يقرأ أو يكتب حقول الحسابات أو الصفقات أو الأوامر أو سجل التداول في `pf_users_data`. تبقى بيانات JSON القديمة دون تعديل، لكنها غير موثوقة ولا تُستورد تلقائياً. تفضيلات الرسم فقط هي التي تبقى محلية. إذا غاب URL أو تعطل الخادم، يتوقف التداول دون fallback محلي.

## حدود الإصدار الأول

1. تداول الحسابات من نوع `PAPER` وفتح/إغلاق/تعديل المراكز والأوامر يمر عبر API الخادمي؛ لا يُعتمد سجل التداول المحلي القديم كمصدر للحقيقة.
2. طلب التمويل يستخدم RPC `pf_create_funding_request` الموثوق. خصم رسوم البرنامج من المحفظة **معطل** إلى أن تنتقل المحفظة إلى دفتر خادمي ذري؛ لا تعتمد الأرصدة المحلية القديمة.
3. لا يوجد استيراد تلقائي لأرصدة أو حسابات `pf_users_data.blob`؛ أي ترحيل يتطلب مطابقة واعتماداً إدارياً موثقاً.
4. migrations مطبّقة على المشروع الحي، لكن جداول المحرك تبدأ فارغة؛ لم تُستورد أرصدة JSON القديمة لأنها قابلة للتلاعب. يجب إنشاء الحسابات عبر مسار ADMIN الموثوق.
5. backend لم يُنشر بعد، و`PLUTUS_ENGINE_API_URL` ما زال فارغاً، لذلك التداول معطّل حتى نشر الخادم وضبط الرابط. خطة Render المجانية لا تضمن عاملاً يعمل 24/7؛ لا تعتمد عليها لمراقبة مستمرة.
6. اختبر بيانات أسعار الأدوات وسياسة انقطاع السعر والهوامش والتزامن قبل إتاحة الحسابات. المحرك محاكاة فقط وليس لإرسال أوامر مالية حقيقية.
